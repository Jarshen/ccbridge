# 工作台单侧换新

从工作台根目录运行命令。日常交流照旧，由收到反馈的一方维护有用的决定，使用原生单向信把会影响搭档的变化告诉对方。两端照常用各自的客户端和审批设置工作。

## 记录方向

`python -X utf8 daily/handoff.py --help` 列出入口。公共参数 `--store` 位于子命令之前。省略时使用环境指定的桥数据库或日常库。复核请指定自己的隔离库。以下用测试配对号 1 举例。

```powershell
python -X utf8 daily/handoff.py --store $bridge show --binding 1 --side cc
python -X utf8 daily/handoff.py --store $bridge note --binding 1 --base 0 --topic 配色 --kind 用户局部认可 --text '用户只认可 v2 的配色，轮廓待比较' --evidence '当前对话中用户对 v2 的原句位置' --file $sample
```

第一次的版本号为 0，以后沿用刚刚核对过的版本号。相同事项追加修订，最新条目供接续，旧条目和原始证据仍可追溯。不同方面分别使用不同事项名。`--file` 可固定实际文件和摘要，替换该文件会阻止按旧交接包接管。使用独立的版本文件可保留原件。模型观察、用户原话、局部认可和整体验收分别有自己的类型。技术细节用 `--audience desktop`，两端都要遵守的条件保留默认 `both`。双方均能发起记录；不要求用户填表。

## 换新一个端点

1. 在原端项目目录的原生客户端创建一个新聊天，完成一次就绪回合，保留旧聊天和搭档。Claude 选 CloudCLI 的应用会话 ID，可从会话链接取得。Astra 选 Desktop 的线程 ID，在新草稿发送首信。此时旧配对继续工作。
2. 从原配对准备交接。记录实际未完成的工作、在途工作如何处置及接手方。指定当前客户端实际使用的只读索引。`--expect` 可重复，用于核对图标文字、样品版本等已知事实，这些值不会写入候选提示。需要主观判断时由用户看原样品和答复。
3. 新 Claude 在 CloudCLI 中发送独立一行 `接续检查 <ticket>`。新 Astra 在自己的原生回合查看该 ticket 的 packet，按提示回查文件，在最终答复最后一行写 `接续核对 <ticket>`。只在候选端打开与其职责相关的材料。
4. 核对候选的实际答复、未完事项和原生端状态。使用 `request` 请求接管，然后用 `status` 查看结果。只有 `committed` 和新的 `successor` 配对号代表交接完成。两端收到新配对说明后再继续任务。交接窗口内保持两端空闲，待办按交接包中的归属执行。
5. `blocked` 的 detail 给出原因。仍有信或运行中的回合时，到原地址查看并等待真实结果。材料、方向、原配对或服务实例变化后重新准备。仅见入队回执且找不到目标原生历史的信会阻止接管。历史上使用实验性 strict_route 的配对也会保留原状，常规严格收件配对可继承其收件模式。

```powershell
python -X utf8 daily/handoff.py --store $bridge prepare --binding 1 --side cc --index $cloudDb --candidate $newCloudSession --work 'Astra 已交付 v2；接手 Claude 核对配色，用户尚未接受轮廓'
python -X utf8 daily/handoff.py --store $bridge status $ticket
python -X utf8 daily/handoff.py --store $bridge request $ticket
python -X utf8 daily/handoff.py --store $bridge status $ticket
```

换 Astra 使用 `--side desktop --index $desktopState --candidate $newThread`。候选仅能接管同一侧同项目；保留搭档原地址。旧配对、旧信、领取记录仍按原 ID 查询。已传输或已读只说明传输阶段；任务结果看实际产物。准备和核对阶段可用 `cancel $ticket` 撤回。已提交后不能用 cancel 倒拨数据；需停止继续执行并核对双方原生历史与队列，再通过新的显式交接转移职责。

## 启用及复核

已运行的生产主机继续使用启动时载入的代码。本次没有重启日常服务。以后要体验时，在现有工作都结束后通过原工作台入口正常重启带桥主机。没有启用换新的配对继续用原流程。停止使用新功能无需删除数据库；不主动请求接管即可。已有会话可由代理通过本页找到入口。

本地可运行 `python -X utf8 daily/launcher.py --doctor`。隔离回归使用 CloudCLI 的 Electron Node 模式运行 `--test daily/test-handoff.mjs daily/test-worker.mjs daily/test-provision.mjs`。

## 评审结论与决定来源

Astra 发起共享评审时在原 send 命令加 `--review`。完成的 Claude 评审回合会把简短最终答复交给 Astra，工具日志留在本端。Claude 也可用 send 的 `review_to` 提前交付；原委托只关联一封结论。反向可由 Claude 用 send 的 `review=true` 委托，Astra 通过 `send --review-to <原信 UUID>` 回传。普通通知沿用原入口。用原信编号查询 receipt，或在消息详情查看“依据”，可区分待结论、已登记、原生队列接收和目标已收到。失败或结果不明时先查原生聊天，按原编号核对；需要结束未回传的评审时，使用 `handoff.py close-review --binding <配对号> --request-id <原信 UUID> --reason <实际处置>`。

代理可对同一事项分别写 `--kind 用户授权 --source 用户`、`--kind 方案建议 --source Opus` 和 `--kind 实测事实 --source Astra`。每条 note 仍引用原话或证据，并使用当前版本号。show 与交接包会并列保留这些来源，各自的新修订更新对应条目。来源未标注的历史记录保留原有文字。用户直接在任一侧裁决即可。
